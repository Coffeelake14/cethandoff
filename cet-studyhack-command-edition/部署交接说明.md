## 3. 两处关键修复（务必保留）

### 3.1 配额写入 `insertIfAbsent` 必须传冲突目标（根因修复）

- **现象**：function_backend SDK 的 `insertIfAbsent(row)` 若不传冲突目标，返回 `database_invalid_operation`，
  导致所有配额写失败 → fail-closed 拒绝**全部** AI 请求。
- **依据**：官方 `assets/function-backend/routes.mjs` 要求 `insertIfAbsent(row, { onConflict })`。
- **修复位置**：`functions/quota.mjs:143`（`CONFLICT_KEYS` 映射）+ `:151` 包装器：
  ```js
  const CONFLICT_KEYS = {
    ai_budget: 'window_start',
    ai_issuance: 'ip_hash,window_start',
    ai_visitor_usage: 'visitor_hash,window_start',
    ai_usage_log: 'reservation',
    ai_resource_bindings: 'binding_key',
  };
  async function insertIfAbsent(table, row) {
    const onConflict = CONFLICT_KEYS[table];
    return execute(`${table}.insertIfAbsent`, db.from(table).insertIfAbsent(row, { onConflict }).select('*'));
  }
  ```
  `.select('*')` 回传插入行；空数组表示已存在（幂等）。`ai_reservations` 用普通 `insertRow`（无需 onConflict）。
- 若团队后续新增表或改主键，务必同步 `CONFLICT_KEYS`。

### 3.2 拍照压缩上限对齐上游请求体硬限（scan 大图失败修复）

- **现象**：公开站"拍照导入原文"对密集照片报"暂不可用，请重试。"（`ai_service_unavailable`）。
- **根因**：上游 QCA 模型请求体约 **256KB** 硬限；旧前端 `scan.js` 压缩上限 `MAX_DATA_URL=1800000`（~1.8MB）远超该限，
  密集照片压缩后仍 >256KB → 上游快速失败。
- **修复位置**：`web/scan.js`
  - `MAX_DATA_URL` 1800000 → **250000**（留 margin）；`MAX_EDGE` 2000 → **1600**；新增 `MIN_EDGE=800`。
  - `compressPhoto` 重写：JPEG 质量 0.85 起步，超限时 q 0.78→0.5 步进 0.07；质量压不下时**分辨率递减**
    （`edge*=0.8` 重渲染）直到 ≤cap 或触底 `MIN_EDGE`；仍超则抛"照片内容过多，请只拍一页并靠近一些。"
  - 三处拍照入口（阅读工具 / 估分写译 / 自带材料）都经 `transcribePhoto→preparePhoto→compressPhoto`，一处修复全覆盖。
- **验收**：最坏情况 2000×2600 随机噪声 PNG（原始 17.89MB）→ 压缩 222251 字节 ≤cap；整页真实 CET-4 阅读原文
  → 压缩 204991 字节 → 真实 OCR 高可信度、1112 字准确转录、7.2s。
- 注意：`scan` 服务端仍校验 Base64 长度 ≤6,000,000、解码 ≤4MB、magic bytes 与声明 MIME 一致——这些是**安全校验**，
  与上游**请求体硬限**是两回事；前端压缩上限必须同时满足两者，当前 250000 已满足。

## 4. 数据库与配额结算

### 4.1 6 张表（`schema.sql`，app schema）

| 表 | 主键 | 用途 |
| --- | --- | --- |
| `ai_budget` | `window_start` | 按 UTC 日窗口的预算与已花费 |
| `ai_issuance` | `ip_hash, window_start` | 每 IP 访客签发限流 |
| `ai_visitor_usage` | `visitor_hash, window_start` | 每访客请求上限 |
| `ai_reservations` | `reservation_id` | 预扣（reserve）记录，带 TTL |
| `ai_usage_log` | `reservation` | 结算（settle）幂等日志 |
| `ai_resource_bindings` | `binding_key` | Agent/Environment 协调器锁与绑定 |

### 4.2 结算设计（团队既定，非 bug）

- `handler.mjs` settle 用 `usage.totalCredits`（来自官方 `session.usage` 事件）。
- **本环境 provider 不发 `session.usage.total_credits`（恒 null）** → settle 记 `usage_missing`，保留全额预扣
  （`CET_AI_RESERVE_CREDITS`，当前 200），由 cleanup（10min TTL）到期保守扣减。
- 结果：**fail-closed 永不超支**，但按预扣额（200/次）计耗，约 50 次即耗尽 10000 日预算。
  如需更宽松，可调低 `CET_AI_RESERVE_CREDITS`（须 >0 且 ≤日预算）。
- `usage.requestCredits`（来自 `span.model_request_end`）仅用于 UI 展示，不参与结算。

## 9. 已知限制

1. **网关 SSE ~60s 硬截断**（平台层，非代码回归）：单条 Function SSE 流约 60s 被截断（ERR_HTTP2_PROTOCOL_ERROR）。
   当前各 action 输出都短（train 短 JSON / explain 单节 / grade 短 JSON / recommend / scan），正常不接近该窗口。
   **不要重新引入"一次返回全部"的长请求**（旧 analyze 已移除）。心跳 15s 与 MAX_STREAM_MS=120000 都不能阻止该硬截断。
2. **配额按预扣保守计耗**（§4.2）：provider 不发 total_credits 时按 200/次计，约 50 次耗尽日预算；可调低预扣。
3. **拍照上游 ~256KB 请求体硬限**：前端已对齐（§3.2）；极密集整页可能触底分辨率或提示"只拍一页并靠近一些"。
4. **真实手写 / 反光 / 竖拍方向**：印刷体已实测；真实手写准确率、HEIC（不支持，需转 JPG）仍需真机复验。
5. **持久化**：学习资料/进度在浏览器 localStorage，跨设备与清缓存后不可恢复；私有数据库只存额度/绑定/脱敏运行记录，

6. **预置题与题库双份维护**：`web/lab-data.js` 与 `functions/lab-bank.mjs` 内容对应，改一处需同步，`test-lab` 校验两边。
